# Remaster window and presentation

October 16, 2026, branch `remaster`, based on `b15e6ff`. This is a user-authorized modernization of the Windows frontend, not an ASM-equivalence correction. Original gameplay rendering and simulation remain in place.

## Window and monitor behavior

[CWindow](../src/X2DWindow.cpp) owns a Unicode Win32 HWND registered with `RegisterClassExW` and bound through `GWLP_USERDATA`. The process requests Per Monitor V2 DPI awareness before application startup. The frontend requires Windows 10 version 1703 or later. Window creation failure and partial graphics initialization are cleaned up; normal shutdown unregisters input, releases graphics and destroys the HWND.

Fullscreen means a non-topmost borderless window covering its current monitor. It starts on the monitor containing the pointer. `gfx_fullscreen=0` still selects a decorated, resizable window. Alt+Enter switches between the two styles; a previously used window rectangle is restored and constrained to the current monitor's work area. Display topology and DPI changes update placement without requesting a monitor mode.

The desktop resolution, refresh rate and color depth are never set or restored by the frontend. The image, video, loading screen and menu may still request different **internal render sizes** through the existing application API. That replaces only the CPU frame and upload texture, retaining the window, D3D device and swapchain. The graphics-options list now describes internal render sizes, including legacy sizes absent from a monitor's mode list.

Selectable render sizes use 32-bit color exclusively, with one entry per width/height pair. The list is sorted by ascending pixel count, then width and height for equal pixel counts. Captions contain only the dimensions (for example, `1920 x 1080`). Startup and resolution changes use 32 bits even with an older `gfx_screen_depth` or `intro_screen_depth` setting; indexed/RGB565 source assets retain their existing conversion support.

## Presentation

[CDisplay](../src/X2DDisplay.cpp) replaces `CDDDisplay` and its exclusive DirectDraw primary/back surfaces, palettes, clippers and flips. D3D11 uploads an opaque BGRA image to a dynamic texture and draws it through a two-buffer DXGI `FLIP_DISCARD` swapchain. Presentation uses vertical synchronization. Hardware device creation has a WARP fallback; removed/reset devices release their graphics resources and attempt recreation on a later update.

The existing software renderer still produces indexed, RGB565 or BGRX bitmaps. Indexed palettes and the existing 16-to-32-bit conversion table feed the BGRA frame. Native bitmap origins, row strides and clipped placement remain respected. The GPU preserves aspect ratio with black bars. Automatic sampling uses nearest-neighbor for 1:1 and equal integer enlargement on both axes; fractional enlargement and reduction use bilinear filtering to avoid unevenly replicated source pixels. This smooths existing detail without reconstructing higher-resolution assets. There is no claim that the game renderer itself has been ported to GPU drawing or Direct3D 12.

The supplied 2560 x 1440 screenshot has an active image from x=320 through x=2239: 1920 x 1440, exactly 4:3. It does not demonstrate geometric stretching; fractional nearest-neighbor scaling is a plausible source of the observed uneven text and sprite edges. The automatic filter change still requires visual runtime confirmation.

Mouse positions use the same presentation rectangle as the GPU viewport. Borderless fullscreen confines the pointer to the visible image, keeping edge scrolling reachable even with black bars. Position locking and configured mouse subareas are transformed into physical screen coordinates. Relative Raw Input sensitivity is retained. Absolute/remote devices are confined without single-pixel warping. Focus loss, minimization, modal loops and shutdown release confinement; focus return restores it. The existing debugger exemption remains: clipping and warping are disabled while a debugger is attached.

Custom hardware cursors use the same physical content-height / 768 scale as the GUI, including their hotspots. The owned resized cursor is cached until its source or output size changes, and released after switching away from it; source cursor handles remain borrowed. Normal/pressed/right modes, window resizing and client-area cursor messages use that cache. Software cursors already draw on the scaled GUI canvas. Normal Windows arrow/wait cursors retain their system handling.

Client `WM_SETCURSOR` handling returns zero inside the existing dispatch protocol, suppressing `DefWindowProcW`; the outer window procedure then returns Win32 `TRUE`. Returning `TRUE` inside the internal handler incorrectly requested default processing and let the class cursor overwrite the game cursor, causing the user-reported flicker. The corrected window handler and its application/cursor consumers pass `/Zs /W4` without warnings. The user subsequently accepted the resulting output on October 16, 2026.

## In-game HUD scaling

The in-game and main-menu desktops use a separate GUI canvas with a reference height of **768** pixels. Its width follows the selected world's aspect ratio (`round(worldWidth * 768 / worldHeight)`), so widescreen displays gain horizontal space while controls retain the apparent size of the 1024 x 768 reference. The main world bitmap and its camera remain at the selected native render resolution. The main menu's animated background also retains native resolution and its original color remapping; its logos, buttons, text, campaign maps, submenus and dialogs draw on the scaled GUI plane. Closing either desktop clears its presentation bindings before the next screen opens.

`CDisplay` composites the world and GUI as separate D3D11 textures. The GUI canvas uses premultiplied RGB and inverse coverage in its high byte: `0xFF000000` is transparent, ordinary packed RGB paint is opaque. Existing scalar/fast GUI alpha and shadow drawing preserve that coverage only on this canvas and its scratch frame; ordinary world/asset surfaces retain their previous behavior. Clearing and redrawing the GUI each frame avoids stale panels. GUI GPU resources follow device recreation; borrowed desktop/world pointers are cleared when the in-game desktop closes.

Mouse screen mapping targets GUI coordinates while the HUD is active. Main-world hit testing and dragging convert those coordinates back to native world-display pixels. Selection rectangles, object tooltips and pause text use the GUI plane; camera motion and world rendering keep their established native coordinates. In-game screenshot export composites both planes at the selected native resolution.

The small minimap's image area is **224 x 224** GUI pixels instead of 112 x 112, at every resolution. Its window is 257 x 241, with the map at (0, 17), reaching the left and bottom screen edges without the former enlarged black padding. The window includes the top ornament in hit testing, preventing clicks through it into the world just as on the right rail. Controls sit beside the larger image. The remaining narrow dark edge inside the map is retained at the user's request; no extra map crop is applied. The original alpha frame (`ls_gui_window.bmd`, bob 0x37, type 4) measures **149 x 133**, including its right shadow; the former 140-pixel scratch buffer clipped nine columns. Its complete bounds now size the scratch buffer. Nine sections expand the original opening (4, 17, 112, 112), retaining the top/right border thickness and alpha shadow rather than doubling them. The existing overview renderer and coordinate transforms receive the new map dimensions, retaining map navigation and zoom handling. Windows draw code at `004C9824..004C985D` already calls the shaded-alpha renderer for this frame; no alternative opaque frame was substituted.

The frame dimensions and alpha format were checked against the installed Windows data archive. A private asset preview verifies the frame section geometry and edge placement. The minimap window and three main-menu implementation units pass Win32 `/Zs /W4` syntax checks, with two existing `sessionName` shadowing warnings in the manager. No build or game run was performed for these follow-up changes; verify menu clicks, campaign selection, main-menu/game transitions and the minimap shadow in the executable.

Ten affected implementation units pass Win32 syntax checks; the final `/W4` pass reports only the existing shadowed `display` local in `WorldDisplayElementAccess.cpp`. The final coordinate/screenshot units also pass separately. World, GUI and vertex shaders compile as Shader Model 4.0. No new executable build or game run was performed for this change. The 1024 x 768 versus 1440p visual comparison, minimap interaction, dialog dragging, screenshots and resolution transitions require runtime confirmation. Sound/music focus behavior was not changed.

## Video integration

Title and mission FMVs no longer read COM interfaces from the display object's native offsets. [CVideoPlayer](../src/WindowsVideoPlayer.cpp) owns a separate, nonexclusive DirectDraw decoder object and the existing Windows multimedia stream. Its decoded RGB sample is locked and copied into `CDisplay`; it never creates the game's primary surface or changes display modes. Audio, filenames and skip controls retain their existing routing. Partial-open cleanup and COM initialization are balanced.

At the user's request, video frames fill the complete window client area, stretching independently of the selected game's aspect ratio. Decoded pixels retain their source dimensions in an owned frame bitmap and GPU upload texture; D3D11 uses bilinear sampling even at integer enlargement. They no longer occupy a corner of a larger game-resolution bitmap. The shipped `intro.mpg` is 640 x 480 with a 640 x 400 picture: its encoded 40-row top/bottom mattes are excluded from the locked presentation rectangle before scaling. This asset-specific crop is limited to that filename and resolution; the full-height `Seq_0000.mpg` is not cropped. Both installed Windows assets were independently decoded for inspection using the locally installed VLC library in a private script; VLC is not a game dependency. This does not verify the game's Windows multimedia decoder at runtime.

The loading indicator scales its original 84 x 4 shape, pulse and two-pixel bottom spacing by loading-bitmap height / 768. Its original animation phase remains unchanged. Loading images suppress the next desktop's GUI overlay while that desktop is being initialized; the next native world frame restores normal GUI composition.

The six affected implementation units pass Win32 `/Zs /W4` checks without warnings (`cursor-loading-video-syntax.log`). No game build or runtime validation was performed for this follow-up. Verify pointer size/hotspots in all three modes, loading phases, video smoothness/stretching/skipping and the top minimap hit area in the executable.

The decoder still depends on legacy Windows multimedia components and installed MPEG codecs. Removing that dependency is a separate media-backend task. Replacing the display backend does not establish successful playback.

## Removal of obsolete 16-bit output paths

The subsequent user-authorized cleanup makes `CDisplay::IsSupportedMode` accept **32-bit output only**. Title and mission-video startup no longer probe or select a 16-bit fallback or read the ignored `intro_screen_depth` override. The desktop-query fallback is also 32-bit. Generic indexed/RGB565 bitmap inputs and 16/24/32-bit decoder input conversion remain supported.

The terrain Gouraud shader now contains only its six 32-bit scalar/MMX variants. The 16-bit entry points, RGB555/RGB565 packing, conversion-table reads and depth dispatch branches were removed. Existing 32-bit masking, fixed-point steps and scalar/MMX alpha differences are retained. Menu/in-game palette remapping no longer allocates, reads or frees the obsolete 65,536-entry high-color tables; the 32-bit palette paths remain. Unused associated constants and offset aliases were removed without changing object sizes or serialized layouts.

The old rain/snow/sand routines rejected non-16-bit targets before drawing, so they already produced no pixels in the 32-bit remaster. Their packed-color lookup allocation and cleanup were removed. At the user's subsequent request, the drawing module and foreground hooks were restored with the 32-bit implementation described below. The weather manager, density state, simulation and savegame support remain unchanged throughout.

The shared bitmap/palette/BOB compatibility library retains its packed-16-bit operations because it also handles legacy bitmap objects, not just screen targets. Likewise, 16-bit file fields, RLE words, map coordinates, fixed-point/MMX arithmetic and audio samples are unrelated to display color depth and remain intact.

The cleanup checkpoint passed Win32 syntax checks for all **306** implementation units present before the weather port. The full `/W3` pass reports the same three existing warnings in `XCrtFileAccess.cpp`, `C2EngineMacroMaps.cpp` and `C2VehicleLifecycle.cpp`; the affected-unit `/W4` check also reports existing local-shadow/unused-parameter warnings in the world/display code. Restoring the ported weather module returns project/filter parity to **307 CPP + 288 headers**. No build, tests or game run were performed. Cleanup verification artifacts are in `.codex-work/32bit-cleanup/`; visual comparison of terrain, alpha edges, palette darkening and video transitions remains the next validation step.

## 32-bit weather overlays

[Weather drawing](../src/C2EngineWeatherDrawing.cpp) now writes directly to the main world's BGRX bitmap. The original foreground order is restored: rain, snow and sand after landscape/creatures and before tooltips/debug overlays. Per-display enable flags and the original `LOD == 2` / `ZoomCounter >= 0` gate remain. Pixel addressing respects the bitmap's row stride and original two-pixel clipping margin.

Windows assembly and Game.exe establish the unchanged density formulas, local random seeds/call order, time factors, camera-relative origins, speed tables and particle shapes. The port applies the original per-channel additions/divisor to full eight-bit channels: rain adds (50, 50, 70), snow neighbors add (170, 170, 170), and sand uses (channel + (300, 300, 200)) / 3, saturating at 255. Snow centers use white instead of the old format-dependent packed `0x7FFF` value. The high BGRX byte is preserved. This color/storage adaptation is authorized remaster behavior, not an assertion of byte-identical 16-bit pixels. There are no per-display lookup allocations and no RGB565 dependency in the weather renderer.

The source audit matches **705** original instructions against Windows Game.exe, all **320** speed-table bytes and all density constants. A source comparison confirms unchanged movement, density, random-call, clipping and write order after isolating the color/storage adaptation. Both affected implementation units pass Win32 `/Zs /W4`, with only three existing unused-parameter warnings in `C2EngineDisplayAccess.cpp`; the weather module is warning-free. Artifacts are in `.codex-work/weather32/`. The user confirmed the current implementation works in-game on 2026-10-16. Broader density, scrolling and zoom coverage for all three weather types remains a follow-up; no game build or run was performed by the agent.
