# Windows human appearance data

Reviewed 2026-10-13 against Windows x86 assembly and original `Game.exe`.

The complete static region at 00568590 occupies 968 bytes: six count/pointer DWORDs, eight male/female name-array pairs, then ten 88-byte player-color records. `SHumanMiscData` documents that layout; existing raw storage and lifetime wrappers remain in use. Its color subregion starts at +0x58. Construction clears the whole region, loads random palettes, job graphics and names in that order, then constructs the color records. Destruction releases each patch array, the patch-set and graphics arrays, male/female string objects, then clears the region in the original order.

Job graphics share a 116-byte prefix: tribe/job, five possible 12-byte body records and five possible 8-byte head records with their counts. Body records store variant ID and borrowed body/shadow bob managers; head records store variant ID and a borrowed head manager. Base records extend that prefix to 188 bytes with three five-choice lists: body palettes, head palettes and random patches. Change records are 120 bytes and instead end with one random-patch ID. The different meanings of +0x74 have separate names. Parser equality limits, input/read order and pointer ownership are unchanged.

Base lookup follows the existing parent-job chain and eventually returns the first base record. Change lookup follows the same chain and eventually returns null. Creation preserves the Windows sequence of random body/head/palette/patch/name choices. Job changes match the existing variant ID, use the first supported entry when unmatched, and retain the variant field; the job patch precedes a soldier's armor patch. No fallback or random call was added.

A random-palette set is 180 bytes: a 40-byte name, patch count/pointer, destination-range count and 32 range slots. Each 16-byte patch stores destination range, optional palette16 ID, optional source range and weight. The destination/source split at 16 distinguishes body from head; the local range is masked to 15 and copies 64 bytes. Both optional IDs start at -1. Name loading still copies 39 bytes into cleared storage, and destination-range insertion remains unchecked beyond the original fixed capacity.

Weight sums retain DWORD overflow. Selection retains the native signed comparison, including the original unchecked exhausted-pointer case. Deterministic selection uses zero and consumes no RNG; random selection consumes its call before source/destination validation. Null palettes, missing source ranges, palette-cache invalidation, self/overlapping copy behavior and call order are unchanged. Locals now identify destination ranges rather than generic types.

Player-color records name the display color, male/female patches, ten inhabitant signs, five soldier signs, road/wall markers and player/ship palettes. The constructor derives its display color from entry 10 within the selected palette range; the +0x2C sample includes the palette's four-byte color-data prefix. Negative player handling and fallback color 9 remain exactly as the individual getters implement them. The separate good-graphics table keeps 66 signed patch IDs and its 264-byte size; its initialization and unchecked negative-input behavior are retained.

Ten source/header files changed. Exact original/staged/source comparisons pass. All 307 production C++ units pass Win32 `/Zs`, with `/arch:IA32` for CRT math; the final table naming and 85 compiler value/type pairs pass targeted checks. Structured record/region/member assertions preserve all sizes and offsets. Five existing byte/bool warnings remain unchanged. 1605 targeted native instruction byte sequences verify against `Game.exe`. No build, tests or game run occurred. Static checks and disassembly provenance do not establish complete runtime equivalence.

Field semantics and layouts come from Windows stores, consumers and lifetime paths. Mac references supply corresponding object/function names only; original member spellings are unresolved. See `HUMAN_APPEARANCE_FIELDS.csv`. The whole-source review continues with remaining static animation/walk lookup structures, display state and GUI/control/data layouts.
