# World-display GUI widget storage

Named the widget's bitmap/display, input flag, hovered object, human/vehicle interaction actions, two command buffers, area-selection state and coordinates, frame mode, click callbacks, event time, follow state and darkening resources. Character preview and observation-window consumers use the same display fields. Existing input-manager, engine-display, object-reference and network-command definitions are reused.

Windows `004BA042..004BB744` establishes construction, message handling, object picking, command preparation, area selection, follow mode and darkening. The widget is `0x244` bytes. Its state begins at `0x30` and spans 532 bytes. The object under the mouse is the established 396-byte engine search object at `0x38`. Two 20-byte commands begin at `0x1CC/0x1E0`. Mouse selection uses world-pixel coordinate pairs at `0x1F8/0x200`. Follow state occupies 24 bytes at `0x220`. Darkening keeps the variant, palette and high-color lookup table at `0x238/0x23C/0x240`.

The embedded state constructor receives root `+0x30`; its relative map-coordinate fields at `0x0C/0x0E` and command buffers at `0x19C/0x1B0` have a separate namespace. Physical models keep flag padding explicit and do not alter allocation or object lifetime. Hovered human/vehicle/house/player aliases are checked against the existing engine reference's member offsets.

Preserved: constructor-before-reset order, search-object resets, primary/secondary command order, per-member command copying, responding sounds, area-selection coordinate conversions, wrapped distance comparisons, callback dispatch, the existing event-time compatibility adapter, human-before-vehicle follow validation, revision checks, camera offsets, palette ownership and 16-/32-bit remap arithmetic.
