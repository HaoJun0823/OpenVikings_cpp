# Multiplayer goal records review — 2026-10-15

Baseline `510efc4`. Windows assembly and original Game.exe establish widths, layout, selectors and call order. Mac header declarations supply corresponding manager/method names only. This is a naming/layout review of the existing manager and connected consumers, not a claim that all multiplayer gameplay paths were executed or every transitive callee audited.

The complete 0x740-byte manager has an enabled byte, twenty twenty-byte result records, separate next-win/next-loss order counters, loaded goal count and twenty 0x48-byte goal records. Result records retain separate won/lost bytes, DWORD order values and a pending-removal byte. Documentary views cover the manager, its interleaved result columns and all tagged goal payloads: eight good/amount pairs, population threshold with soldiers-only byte, or twenty mission-trigger flags. Unused spans remain explicitly unclassified; the generic payload remains raw bytes. No live casts or replacement constructors are introduced. Goods-count scratch storage is a DWORD total followed by sixty-six WORD counts, exactly 136 bytes.

The loader enables goals only for map type four, writes the initial survive goal and count one, then processes the four known commands. Existing payloads are not cleared. Goal capacity is checked by equality with twenty, and pair capacity by equality with eight; no broader guard is added. Parameter order and signed/unsigned consumption remain unchanged. Four token records and their null terminator at 004F3820..004F3847 match PE strings and IDs. Lazy initialization flags, the retained pointer and bare-RET exit-callback adapter remain unchanged.

Evaluation still scans all twenty players and all twenty goal slots, independently of the loaded goal count. The repeated won/lost query and active-player check remain. Goods use WORD counters promoted for signed comparison against signed amounts and a signed pair count: zero requirements win; a negative count does not. Population uses unsigned comparison and selects total humans or soldiers, not adults. Good IDs and mission-trigger player IDs remain unchecked. Win/loss flags, order writes/increments and callback 0x30 retain their native order. The pending-removal flag is written after the loss callback returns. Callback mutation opportunities are not hidden by cached replacements.

The type-one callback keeps its 120-tick cadence and executes pending removals before checking goals. A pending flag is cleared before activity checking and before command 0x89 is queued. No enabled guard is added to evaluation or to the callback. Construction publishes the owner, clears the same full span and registers the same tag/priority; destruction unregisters and clears the owner. Version-one save/load and checksum retain all 1856 bytes, including unclassified bytes and unused goal slots. Unknown save versions still skip the chunk without registering the callback.

The connected mission triggers, GUI-required predicate, network goal/ranking page, onscreen goal captions and goods statistics now use the same named layout. GUI iteration deliberately retains the loaded count and its different signed display of amounts. Ranking arithmetic, sort order, repeated local-player calls and one-based displayed orders remain unchanged. Compound statements were split for readability, including surrounding network-window code, while frozen operation comparisons cover every changed C++ unit.

Evidence regions: 00419032..004195D2 (construct/destruct, save/load, checksum, parser, triggers and evaluation), 00440A53..00440AF7 (goods counts), 004408EE..004409C0 (human counts), 004C53C0..004C5F93 (network-window rendering context), 004B86C8..004B8A09 (onscreen captions). **1,766 instruction instances** match the original PE bytes. These regions establish provenance and the described field/ordering evidence, not a blanket per-instruction transitive-equivalence claim.

Frozen stages retain C++ operation tokens after value/identifier normalization and formatting. **57 distinct value/type comparisons, 33 physical assertions and 151 named layout references** pass across thirteen changed production files. Eight owning/dependent production units plus the private assertion unit pass Win32 `/Zs` without diagnostics. Registration remains 307 CPP / 288 headers; no build, tests or game run. All 47 raw numeric accesses in the owning manager become zero; connected consumers remove another 37 candidates. Repository scan: **2,975 → 2,891**. The broad whole-source review remains open.
