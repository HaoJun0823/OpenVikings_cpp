# Village, house and resource AI records

Named Windows village lists, village state, house/stock/defence lists, resource manager tables, resource search descriptors, good requirements, export lists and invalid-area fields. Constructors, building decisions, object-use checks and production consumers use the same definitions. Physical storage models document these records without changing production allocation/access behavior.

Windows evidence: `004289CD`/`004292E8`/`00429301` constructors; `00453648..00453CC2` village lists and pending requests; `00456449..004571CD` resource initialization, search, updates, exports and invalid areas; `00471418..00472A82` village/house decisions; `00476C43` tower scan cursor. Mac supplies matching class and method names only.

The village list has counts at zero/four, eight physical slots starting at eight, and a pending request at `0x6788`. Each physical slot is `0xCF0` bytes: an active byte and padding followed by a `0xCEC` village. Legacy `slot` locals address eight bytes before their physical slot. The separate slot-view namespace accounts for that bias. The pending packed point at `0x6792` is represented by two WORDs, preserving its unaligned location.

A village holds its ID/player/center/radius, a `0x258` house manager at `0x1C`, goods storage at `0x274`, separate build/upgrade records at `0xCC4/0xCD0`, tower cursor at `0xCE0`, type at `0xCE4` and resource good at `0xCE8`. Village `0x14..0x1B` remains unresolved. House state includes home presence, remembered count, lost-house flag, 55 build flags, ten stock references, 100 defence points and a barrack ID. The stock-pending flag also marks demolition or incomplete construction, as the original condition does.

The `0xD20` resource manager contains player ID, 20 physical resource points, 88 landscape indices, count/cursor, 66 good requirement records, 55 house-good entries and 55 export lists. Legacy `Resource()` pointers address four bytes before a physical point. The search descriptor receives the physical point array instead. Separate namespaces keep these two views distinct: physical offsets 12/16 are minimum valency/stored landscape; folded offsets 12/16 mean good/minimum valency. Unexplained point/requirement padding remains explicit.

Preserved: initialization does not add new clears; village initialization retains its existing count; missing village ID returns the first slot; search order, score ties, danger calculation, exclusive area edges, partial flag updates, no-valid-resource sentinel, worker selection, build status codes and callback order remain unchanged. Tower cursor is distinct from the house manager's byte home flag. Goods-manager internals beyond the selected consumers are not claimed complete.

Validation: exact staged baseline/source-token equivalence, 117 literal value/type pairs, 66 physical-layout assertions, affected-unit Win32 `/Zs` checks and native byte checks against original `Game.exe`. The companion CSV records 362 named field/size references. No build, tests or game execution. Remaining raw operands and explicit unknown regions continue to require review; this closes the selected record block rather than the whole-source task.
