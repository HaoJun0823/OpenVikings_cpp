# Shared DirectDraw palette and window/display ownership - 2026-10-11

Four previously unmapped entries are explicit: the window destructor forwarding entry, the two existing fullscreen-aware offset getters and the palette allocator. The already mapped display-deletion body is retained separately. See [SHARED_DISPLAY_NATIVE_ENTRIES.csv](SHARED_DISPLAY_NATIVE_ENTRIES.csv).

The palette allocator calls original malloc entry 004E85FC (Runtime_Allocate), allocates 0x408 bytes, writes version 0x0300 and 256-entry count, and leaves the final four allocation bytes untouched. Native startup at 0047ABFA calls it unconditionally, replacing the member pointer. It clears all four bytes of each of the 256 palette entries in blue/green/red/flags order. Previous C++ reused an existing allocation and initialized a gray ramp. Startup now follows the original allocation and black initialization; the existing destructor uses Runtime_Free as original 0047ABCC does. No new allocation-failure fallback is invented; native allocation proceeds to header writes without checking null.

Window construction initializes its instance/show-command fields before allocating the 0x54-byte CDDDisplay through 004E5DDD. Construction uses placement new when allocation is nonzero; subsequent native StartUp access is retained without an extra invented null guard. Window destruction at 0047B633 forwards to the distinct 0047B868 body. That body captures the display, calls its destructor, frees through Runtime_Free, and clears the member only when originally nonzero. Matching allocation/free changes are made together. The Windows constructor has no SEH scope prologue; this forwarding entry is not mislabeled as an exception-cleanup routine.

Both window-origin getters return zero in fullscreen and the original signed offsets otherwise. They were already correct inline; making their original entries explicit adds no new graphical feature. Existing application/display callers retain these getters.

These corrections are established from Windows assembly and Game.exe. Mac references provide no established Windows DirectDraw counterpart; current project class naming is retained. This does not establish that the user's green road pixels were caused by the initial palette, nor that those pixels are fixed. Three affected/integrating units pass MSVC Win32 /Zs without diagnostics. Project/filter parity and naming uniqueness pass. No build, tests or game run occurred.
