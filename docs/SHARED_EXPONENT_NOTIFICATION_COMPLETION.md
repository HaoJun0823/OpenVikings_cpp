# Binary64 exponent field and alternate unwind notification - 2026-10-11

Windows **004F1907** is now translated as Runtime_SetDoubleExponentField. The original captures the input's high WORD before its first x87 load/store, then computes a wrapped DWORD `exponent + 0x3FE`, shifts it left by four, ORs the preserved sign/fraction nibble (`originalHighWord & 0x800F`), and replaces only the stored value's high WORD. The final result is loaded into x87. This is a literal field replacement, not ldexp, scalbn, a range-clamped exponent setter, or a copy of a Mac math function. In particular, the exponent-zero call produces the native 0x3FE exponent for frexp's mantissa path.

A small non-inlined cdecl helper returns a loaded binary64 through the Win32 x87 ST(0) return convention. Its result is stored into a volatile double, then read through volatile unsigned-char accesses to retain the binary64 store before editing its object representation. A second call returns the patched result through ST(0). Local precise/exception/environment pragmas keep these operations sensitive to the active floating-point state. No arithmetic host-library replacement, FPU reset, control-word change, SSE arithmetic, inline assembly or new CRT dependency is used. Integer byte reads are explicit because an SSE-only bit copy would omit the original FLD/FSTP NaN, denormal and exception behavior. Native instruction-pointer/data-pointer addresses and the temporary call frames naturally differ in the recompiled program; source completion does not claim binary identity or a runtime exception-handler validation.

The cdecl x86 return contract is also visible in [LLVM's production X86CallingConv.td](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/X86/X86CallingConv.td), RetCC_X86_32_C: ordinary f32/f64 results use FP0 even with SSE2, except separately marked register conventions. The helper explicitly uses cdecl and is not inline. [Microsoft noinline](https://learn.microsoft.com/en-us/cpp/cpp/noinline) and [float_control](https://learn.microsoft.com/en-us/cpp/preprocessor/float-control?view=msvc-160) provide the compiler controls used here. These sources establish adapter contracts, not original math behavior; all original constants/order/field masks come from Windows assembly and Game.exe. No x64 target or calling convention is introduced.

Windows **004EC709** is the second notification entry into the three shared native stores. It takes the code from ECX directly and does not dereference frame+8. Runtime_NotifyNonLocalGotoWithCode retains this distinction through explicit destination/code/frame arguments. Both notification entries remain separate C++ functions and perform ordered volatile writes to the same complete 16-byte notification record. Both return the unchanged destination; neither invokes the destination, performs an OS unwind, changes the original frame's try-level, or reads the consumed extra stack DWORD. The latter work belongs to the still unresolved callers. [SHARED_NOTIFICATION_STATUS_COMPLETION.md](SHARED_NOTIFICATION_STATUS_COMPLETION.md) covers 004EC712 and the record layout.

004EC709 was not in the earlier direct-call/table inventory. Its separately proven native entry adds one address to the denominator as well as one implementation: the new total is **4667/5063 (92.18%)**, **396 open**. Shared/system helpers are **625/670 (93.28%)**, **45 open**. 004F1907 closes one existing address; no open address is removed. The native frexp parent 004F198A, classifier 004F1A5D, rounding entry 004F1A4B, raw control writer and error dispatch remain open. Inspection of the installed Release x86 CRT _fpclass shows SSE UCOMISD and integer NaN copies where the original uses x87 FCOMP and FLD/FSTP: it is therefore not substituted as an equivalent helper.
