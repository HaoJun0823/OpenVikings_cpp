## Additional masked-response findings from Windows

004F1DA2 initializes remaining flags to input & 0x1F. It checks, in order, invalid input flag 8 against control mask 1, division flag 4 against control mask 4, overflow flag 1 against control mask 8 and underflow flag 2 against control mask 0x10. At most one of these branches is handled before the common end; it then independently handles input inexact flag 0x10 when control mask 0x20 is set. Success means no remaining low-five flags. Do not turn this priority chain into independently handling all four exceptions.

Hardware generation calls receive raw x87 bits: 1 for invalid, 4 for division, 8 for overflow, 0x10 for underflow and 0x20 for inexact. These differ from the input math-error flag positions. Overflow response uses an actual x87 comparison with positive zero, not merely the input sign bit. Nearest rounding chooses signed infinity; toward zero chooses signed maximum finite; upward chooses positive infinity or negative maximum finite; downward chooses positive maximum finite or negative infinity. The original strict-positive versus not-positive distinction must retain its comparison/status effects and unordered behavior.

Underflow first preserves whether input inexact is already set. It copies the result through x87 and compares with zero. Zero/unordered comparison follows the native equality branch. Nonzero results use 004F198A and subtract 0x600 from the returned exponent. Signed values below -1074 take the direct positive-zero path and force inexact; otherwise the routine constructs the significand field and shifts down toward exponent -1021, recording discarded low bits. Negative sign restoration occurs in the shift path, not the direct positive-zero path. The exact literals -1074 and -1021 come from DWORDs FFFFFBCE and FFFFFC03. A guessed frexp/scalbn/signbit/host rounding replacement would hide these distinctions and their x87 effects.

004F2024 is the immediate status-generation dependency. Its original invalid integer conversion, overflowing/underflowing stores, division and inexact store must be reproduced with the x87 unit and native ordering. A modern SSE arithmetic result alone does not establish the same status or unmasked exception path. Installed UCRT and even the older system msvcrt _fpclass use SSE comparisons/copies at the checked entries; they do not supply the original classifier's FLD/FSTP and FCOMP effects. No extra legacy CRT dependency or guessed forwarding adapter was added.

The complete 004F2024 branch order is raw bits **1, 8, 0x10, 4, 0x20**; multiple matching branches execute. The input low byte is captured in CL before any action. Invalid generation loads the 80-bit constant at 0050F254 and FISTPs a DWORD into its own input argument slot, then waits; subsequent tests still use the preserved CL rather than rereading that overwritten slot. The same constant is significand 8000000000000000/exponent 4410, exactly positive 2^1041, beyond binary64 range. Overflow performs a waiting status read before loading it, stores binary64, performs two waits and reads status again. Those otherwise unused reads/waits must not be removed casually.

Underflow uses the separate 80-bit constant 0050F260: significand 8000000000000001/exponent 3000, exactly (1 + 2^-63) * 2^-4095. It stores binary64 then waits; neither constant can be supplied as an ordinary MSVC double/long-double literal without losing the native operation. Division loads zero then one, uses the original reversed divide, pops the result and waits. Inexact loads the x87 pi constant, stores binary64 and waits. The routine does not clear exceptions, reset control, replace the active rounding mode or restore a pre-call status snapshot. It returns with the generated sticky status and any resumed-handler changes retained.
